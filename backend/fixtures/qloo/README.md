# Qloo fixtures (synthetic)

These JSON files are **synthetic, doc-shaped fixtures** for the Qloo API, written before we had a hackathon API key. Their field names and nesting follow the official Qloo documentation (docs.qloo.com, github.com/qloo/docs-public, recipes on the Qloo docs MCP). All IDs (`FA4E0000-…`), scores, rankings, coordinates and most tag IDs are invented for a fictional "Jack Daniel's vs Bad Spaniels" scenario. Each file has a top-level `_fixture` key (`synthetic: true`, a note, and the request that would produce it, plus `http_status` for non-200 cases) that the client must strip before parsing. Shapes that the docs do not pin down are marked UNVERIFIED in `docs/qloo-api-notes.md`. After the live test on Monday, replace these with fixtures whose **shapes** match recorded responses, but keep the values synthetic. **Never commit live Qloo responses.** The hackathon developer guide forbids storing Qloo response data in a public repository, so keep any recordings outside the repo or in git-ignored paths.

`brand_taxonomy.json` is a synthetic 67-node slice of the `urn:tag:genre:brand` tree (real paths, Title-Case names, invented popularity). The FixtureClient serves every `/v2/tags` call that passes `filter.tag.types=urn:tag:genre:brand` from it by substring match on the node name, so the 26 letter queries of `qloo.taxonomy.load_brand_taxonomy` harvest it like the live tree. Compare and insights-tag fixtures follow the shapes confirmed in the live spike (values stay synthetic).

Search fixtures carry the entity's own tags in the live shape (`{"name", "tag_id", "type"}`), including `urn:tag:genre:brand:*` nodes (synthetic choices for Jack Daniel's, In-N-Out, Smashburger), because the universe of a resolved brand is built from them (harness v2). `FixtureClient.target_affinity` (the `filter.results.entities` lookup) answers from an optional `insights_<type>_seed_<seed>_target_<target>.json`, else from the target's entry in the ranked fixture `insights_entities` would serve.
